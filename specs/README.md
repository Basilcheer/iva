# Формальные спеки

TLA+-модели мест, где ошибка — гонка, а не опечатка. Модель пишется по коду как он есть; TLC
перебирает все порядки событий в малых границах и либо доказывает инварианты в них, либо даёт
контрпример по шагам. План и инварианты: `docs/quality/tla-plan-2026-09-26.md`.

## FileLock — `agent/lib/fs-atomic.ts`

Запуск (Java 17, `tla2tools.jar`; обёртка `tlc`):

```sh
tlc -workers 8 -deadlock -config specs/FileLock.cfg specs/FileLock.tla
```

`-deadlock` отключает проверку тупика: завершившиеся процессы (`done`) — нормальный конец.

| Конфиг                   | Что проверяет                                                                                                                                                                                                                                                                                          | Итог (26.09.2026, раунд 4)          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------- |
| `FileLock.cfg`           | 3 процесса, секция быстрее тика: все инварианты (3 — контракт) и живость. `Beat` здесь не исполняется (секция короче периода); граница `MaxTries` достижима — живость с оговоркой ниже                                                                                                                 | проходит                            |

Время в модели идёт свободно; каждое допущение о нём — явная константа:

- синхронные шаги `attemptLock` и `releaseFileLock` короче `staleMs` (они не отпускают event loop);
- `MaxSection` — сколько тиков живой держатель проводит в секции (0 — секция быстрее тика);
- `Heartbeat = TRUE` — асинхронный `acquireFileLock`: таймер держателя созревает раз в `Period`
  (`staleMs/3`), колбэк выполняется не позже `MaxLag` тиков после созревания. `MaxLag` —
  допущение о среде (насколько занят event loop держателя), не свойство кода: время в модели
  ждёт просроченный колбэк, в жизни — нет; `FALSE` — `acquireFileLockSync`;
- `MaxHold` — предохранитель `LOCK_MAX_HOLD_MS`: после него сердцебиение гаснет.

Что проверено в этих границах при допущениях `Period + MaxLag < Stale` и `MaxSection < MaxHold`:
взаимное исключение, owner-файл живого держателя никто не удаляет, живой держатель держит
текущую папку со своим owner-файлом; брошенный замок в итоге забирают, каждый вызов
завершается — на 2 процессах без оговорок, на 3 с быстрой секцией с оговоркой «пока вызов не
упёрся в границу модели `MaxTries`» (см. ниже), на 3 с медленной секцией — только безопасность.
Это проверка в малых границах при явных допущениях, а не доказательство для любых `staleMs`
и любой задержки event loop. В переводе на код: сердцебиение держит живого держателя, пока
между двумя срабатываниями его таймера event loop освобождается хотя бы раз в 2/3 `staleMs`
и секция короче `LOCK_MAX_HOLD_MS`. Держатель, остановленный целиком (SIGSTOP, сон VM, долгий
GC, синхронная работа в том же процессе), не бьётся — его замок забирают, как и раньше.

Что модель не может выдать за доказательство: охрана `~Lagging` в `Tick` останавливает время,
пока просроченный колбэк не прошёл, и модель без шага `Beat` проходит те же инварианты (время
просто стоит). Поэтому свидетель `NotSlow` обязан нарушаться в `FileLock-witness.cfg`: там
живой держатель просиживает в секции дольше `Stale`, и безопасность держится на касаниях.
Вторая проверка: модель, у которой касание не сбрасывает `age`, нарушает `NoSuccessorRemoval`.

Контракт, а не гарантия:

- пустую папку живого претендента может снести параллельная уборка — претендент повторяет
  (инвариант 3); на 3 процессах два претендента могут так сносить папки друг друга по очереди,
  граница модели `MaxTries` достижима (`NoBounded` в 3p-конфигах не включён) — без дедлайна
  это может длиться, с дедлайном вызов вернёт null. Живость на 3 процессах (`FileLock.cfg`)
  считает вызов, упёршийся в границу, завершённым: это оговорка, не доказательство;
- у `acquireFileLockSync` секция обязана быть много короче `staleMs`;
- секция под `acquireFileLock` конечна и много короче `LOCK_MAX_HOLD_MS`;
- у одного пути один `staleMs`: период сердцебиения — из `staleMs` держателя, протухание — из
  `staleMs` претендента.

Порядки событий из контрпримеров на настоящем коде — `agent/lib/fs-atomic.lock-races.test.ts`
(в `npm test`; порядок (а) воспроизводит `scripts/fixtures/lock-race-harness.ts` с подменой
`node:fs` под `--experimental-test-module-mocks`).

### Что смоделировано

- Замок — папка на пути, её поколение (inode) — номер `dir`; владение — owner-файл с токеном
  попытки (`ents`). Токен новый на каждую попытку, как `randomUUID()` в `attemptLock`.
- `attemptLock`: mkdir (EEXIST → inspect) → lstat → open+fstat и сверка идентичности → open "wx"
  owner-файла → lstat → lstat owner → readdir и проверка «та же папка, один owner — свой». Любая
  ошибка после mkdir — catch: удалить свой токен, rmdir. Сверка идентичности не прошла — новая
  попытка без уборки, как в коде.
- `inspectOccupiedLock`: lstat (и протухание по нему) → open+fstat, сверка → readdir → не протухла
  по первому lstat — busy → повторный lstat, сверка с открытой папкой, повторная проверка
  протухания → удалить каждый увиденный токен по одному → rmdir.
- `releaseFileLock`: погасить сердцебиение, удалить свой токен, rmdir.
- Сердцебиение: lstat своего owner-файла, потом utimes каталога — обе операции по пути. Нет
  owner-файла или папки — таймер гаснет. Предохранитель — счётчик тиков в секции (в коде —
  отдельный таймер по стенным часам, не зависящий от периода).
- Живость `EventuallyTaken`: после «замок брошен и кто-то живой ждёт» кто-то живой входит в
  секцию (новый захват: при брошенном замке живых в секции нет по `CrashWindowSafe`) — либо
  ждать некому (вернули null или упали). Временное исчезновение брошенности (кто-то создал
  пустую папку) не считается.
- Петля `acquireFileLock`: busy и новая попытка обе ведут в attemptLock; дедлайн проверяется на
  обоих путях.
- Путевые операции (`readdir`, `rm`, `rmdir`, open "wx", `utimes`) попадают в текущую папку на
  пути, что бы процесс ни открыл раньше.
- Среда: `Crash(p)` на любом шаге (owner-файл остаётся); время — явный счётчик `age` (тики с
  последнего изменения папки), папка протухла при `age ≥ Stale`; папку может удалить и создать
  заново кто угодно между двумя шагами другого процесса.

### Что абстрагировано

- Каждая файловая операция атомарна: так ведёт себя POSIX для mkdir/rmdir/open O_EXCL/unlink.
- mtime — счётчик тиков, а не часы: важно только «прошло ли `staleMs` с последнего изменения».
  Разные часы процессов и ФС, которая неверно ведёт mtime, не моделируются.
- Ошибки ФС, кроме ENOENT/ENOTDIR (EACCES, EPERM, EIO, EBUSY), не моделируются: код на них не
  гасит сердцебиение и пишет одну строку в stderr — это проверяют тесты (инъекция в `utimes`
  через `scripts/fixtures/lock-heartbeat-utimes.ts`).
- Не-папка на пути (v1 lock-file, чужой тип) не моделируется: код на неё всегда отвечает busy и
  ничего не удаляет.
- Чужие имена в папке, не owner-токены, не моделируются: код их не удаляет, rmdir на них даёт
  busy — это только сужает поведение.
- Границы: до 3 процессов, 2 созданных папки на вызов, 1 падение, `Stale` 2–3 тика, секция до 3 тиков
  на 3 процессах и до 4 на 2. Шире на 3 процессах перебор не укладывается в разумное время (больше
  12 млн состояний без конца очереди).
