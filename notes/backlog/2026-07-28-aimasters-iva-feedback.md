# IVA — бэклог жалоб из Aimasters.Me

Собрано из истории чата на 2026-07-28. Запись фиксирует пользовательское свидетельство, не подтверждённый root cause. Статус `закрыт со слов автора` означает, что решение описано в том же треде; его не следует считать регрессионно проверенным.

## Кросс-валидация по коду — 2026-07-28

- **Проверенная база:** `HEAD 62127fa` и текущее runtime-поведение. Локальные незакоммиченные настройки этого VPS не считаются доставленным исправлением.
- **Правило чекбокса:** `[x]` означает, что дальнейшей работы по пункту нет; `[ ]` означает, что остаётся следующий шаг. Тип шага указан в поле `Маршрут`: кодовый PR или исследование.
- **Итог:** IVA-011 закрыт как намеренный product decision. Для десяти кодовых задач заведены issues; IVA-007 и IVA-012 остаются research-first.
- **Штатная проверка:** 228/228 Node tests, TypeScript typecheck, локальный Eve build, 256/256 autograph tests, 45/45 security-defense tests и userbot guardrails прошли. Дополнительные точечные проверки process timeout, reply parsing, Telegram chunking и hard caps описаны в соответствующих пунктах.

## P0 — доступность и потеря ответа

### [ ] IVA-001 — зависший интерактивный subprocess блокирует главный цикл

- **Жалоба:** бот показывает typing, ответа нет; `iva doctor` и `iva restart` не помогли.
- **Свидетельство:** [Руслан, 2026-06-25, msg 6973](https://t.me/aimasters_chat/6973). В дальнейшей диагностике пользователь связал сбой с интерактивным Pi-процессом, запущенным через bash: основной цикл Eve оказался заблокированным ([msg 6987](https://t.me/aimasters_chat/6987)).
- **Гипотеза для проверки:** изоляция и timeout для каждого внешнего процесса; heartbeat должен отражать блокировку выполнения.
- **Медиа:** нет.
- **Статус:** открыт.
- **Маршрут:** кодовый PR [#52](https://github.com/smixs/iva/issues/52).
- **Кросс-валидация:** `частично`. Обычный timeout в `agent/tools/bash.ts` работает, но процесс, игнорирующий `SIGTERM`, оставляет Promise незавершённым; воспроизведено через `trap "" TERM; while :; do sleep 1; done`.
- **Что осталось:** запускать subprocess в отдельной process group и после grace period посылать `SIGKILL`; heartbeat сейчас не видит заблокированный tool call. Тестов на дерево процессов и игнорирование `SIGTERM` нет.

### [ ] IVA-002 — напоминания через workflow раздувают состояние и кладут бота

- **Жалоба:** предложенный агентом `nohup sleep + curl` для напоминаний разрос `.workflow-data` до 700+ MB, CPU достиг 100%, бот перестал отвечать; reboot VPS и `iva restart` не очистили workflow.
- **Свидетельство:** [Руслан Мамыш, 2026-06-24, msg 6870](https://t.me/aimasters_chat/6870).
- **Ожидаемый результат:** напоминания изолированы от agent workflow, есть cleanup/лимиты/диагностика зависших задач.
- **Медиа:** нет.
- **Статус:** открыт; пользователь описал out-of-band workaround на systemd timer и отметил возможные дубли ([msg 6874](https://t.me/aimasters_chat/6874)).
- **Маршрут:** кодовый PR [#60](https://github.com/smixs/iva/issues/60) сразу после #52 и #54, потому что authored tool использует безопасный subprocess и честный systemd adapter. Текущий катастрофический путь ограничен только prompt-запретом и reset; issue добавляет реестр, дедупликацию, reconciliation и диагностику.
- **Кросс-валидация:** `частично`. Инструкция теперь направляет напоминания в `systemd-run`/cron и запрещает `nohup`, а `iva reset` карантинит `.workflow-data`; сам запрет остаётся текстом prompt и легко обходится через bash.
- **Что осталось:** нет реестра, дедупликации, edit/delete, лимитов и диагностики зависших напоминаний. Документация противоречит сама себе: `docs/deploy.md` разрешает Eve schedules, `docs/extending.md` говорит, что они не срабатывают. Lifecycle-тестов нет.

### [ ] IVA-003 — установка иногда падает при активации сервиса

- **Жалоба:** `systemctl --user enable --now iva.service` завершился с кодом 1; пользователь переустанавливал IVA пять раз.
- **Свидетельство:** [Руслан, 2026-06-25, msg 6986](https://t.me/aimasters_chat/6986). Ещё один инсталляционный сбой: `npm exec -- eve build` ([Алексей, msg 6875](https://t.me/aimasters_chat/6875)).
- **Ожидаемый результат:** installer выводит диагностируемую причину и даёт идемпотентный recovery path.
- **Медиа:** нет.
- **Статус:** открыт.
- **Маршрут:** кодовый PR [#54](https://github.com/smixs/iva/issues/54).
- **Кросс-валидация:** `частично`. Build-stage сохраняет полный лог и `iva doctor` умеет пересобрать units, но `enableUnits()` игнорирует exit status `systemctl` и затем печатает успех.
- **Воспроизведение:** stub `systemctl`, всегда возвращающий exit 1, дал сообщение `Units installed and enabled`; реальная причина исходного systemd-сбоя из чата кодом не подтверждена. Тестов failure path для `systemctl` нет.

## P1 — конфигурация и модель

### [ ] IVA-004 — смена модели ломает связку портов и доставку ответов

- **Жалоба:** `iva config` занял 8723 и сменил порт на 8724; после рестарта бот показывает typing без ответа. Смена модели из чата меняет конфиг и тоже оставляет бота без ответов.
- **Свидетельство:** [Руслан, 2026-06-24, msg 6868](https://t.me/aimasters_chat/6868).
- **Ожидаемый результат:** единственный source of truth для `IVA_PORT`/`ASSISTANT_HOST`, preflight до сохранения и smoke test после переключения модели.
- **Медиа:** нет.
- **Статус:** открыт.
- **Маршрут:** кодовый PR [#56](https://github.com/smixs/iva/issues/56).
- **Кросс-валидация:** `частично`. Port preflight, синхронизация `ASSISTANT_HOST` и регенерация units уже есть, поэтому исходный port drift в основном закрыт.
- **Что осталось:** занятый порт принимается за IVA без проверки владельца; ошибка restart игнорируется и CLI сообщает успех; после смены модели нет HTTP/model smoke test. Последнее воспроизведено через падающий stub `systemctl`.

### [ ] IVA-005 — каталог предлагает/принимает неподдерживаемую модель

- **Жалоба:** при запуске `AI_APICallError: Model qwen3.7 is not supported`; бот иногда вообще не отвечает. После ручной правки порта он ожил.
- **Свидетельство:** [Руслан, 2026-06-22, msg 6811](https://t.me/aimasters_chat/6811), восстановление [msg 6812](https://t.me/aimasters_chat/6812), объявление фикса [msg 6815](https://t.me/aimasters_chat/6815).
- **Ожидаемый результат:** модель валидируется против актуального provider catalog до записи конфигурации.
- **Медиа:** нет.
- **Статус:** `закрыт со слов автора`.
- **Маршрут:** кодовый PR [#55](https://github.com/smixs/iva/issues/55); live validation остаётся незакрытым failure mode.
- **Кросс-валидация:** `частично`. Для Ollama/OpenCode загружается live catalog, а OpenRouter CLI выполняет реальный tool-call; Telegram при ошибке каталога откатывается на static list.
- **Что осталось:** текущая модель из `.env`, отсутствующая в live catalog, всё равно добавляется в кнопки и сохраняется без повторной проверки; Telegram-каталог OpenRouter остаётся статическим. Теста на stale current model нет.

### [ ] IVA-006 — большая задержка до первого typing при кастомизации

- **Жалоба:** «работаю» появляется через 20–30 секунд, ответ приходит ещё через ~5 секунд. После factory reset пользователь восстановил быстрый отклик, значит его изменения внесли регрессию; штатного reset с сохранением контента нет.
- **Свидетельство:** [Александр, msg 8268](https://t.me/aimasters_chat/8268), [msg 8281](https://t.me/aimasters_chat/8281), [самодиагностика, msg 8284](https://t.me/aimasters_chat/8284).
- **Ожидаемый результат:** ранний working-status и раздельные latency spans до первого token/status.
- **Медиа:** [вложенный скриншот контекста, msg 8287](https://t.me/aimasters_chat/8287).
- **Статус:** открыт.
- **Маршрут:** кодовый PR [#57](https://github.com/smixs/iva/issues/57) только для early status и latency instrumentation. Factory reset пользовательских source-файлов исключён: безопасного конечного списка нет, риск удаления данных выше пользы.
- **Кросс-валидация:** `частично`. `/new` сбрасывает Telegram/Eve session, а `iva reset` карантинит runtime state и сохраняет vault с `.env`.
- **Что осталось:** нет метрик ingress-to-status, ingress-to-turn, first output и Telegram delivery. Поэтому задержку 20–30 секунд локализовать нельзя. `/new` и `iva reset` сохраняют текущий контракт; source-file factory reset не планируется.

- **Ожидаемый результат:** раздельные метрики provider latency, queue latency и Telegram delivery latency.
- **Медиа:** нет.
- **Статус:** открыт.
- **Маршрут:** research-first; issue создаётся только после измеримого воспроизведения.
- **Кросс-валидация:** `нет подтверждения в коде`. Прямого Google AI Studio provider в IVA нет; Gemini встречается только как модель через OpenRouter.
- **Что дальше:** нужен точный provider/path и trace одного медленного запроса. Запрошенных latency spans в коде нет, поэтому закрывать жалобу как исправленную нельзя.

## P0 — сохранность Telegram-очереди

### [ ] IVA-008 — сообщение, отправленное во время работы агента, теряется семантически

- **Жалоба:** второе сообщение во время выполнения агент «видит», но не выполняет, пока пользователь отдельно не напомнит.
- **Свидетельство:** [Александр, 2026-07-27, msg 8285](https://t.me/aimasters_chat/8285); автор принял баг ([msg 8286](https://t.me/aimasters_chat/8286)).
- **Ожидаемый результат:** явная очередь follow-up сообщений с подтверждаемой обработкой либо честный статус «в очереди».
- **Медиа:** [скриншот примера, msg 8287](https://t.me/aimasters_chat/8287).
- **Статус:** открыт.
- **Маршрут:** кодовый PR [#51](https://github.com/smixs/iva/issues/51).
- **Кросс-валидация:** `частично`. Busy-message сохраняется в очередь и получает 👀, но автоматически после текущего turn не запускается; он приклеивается только к следующему новому сообщению пользователя.
- **Подтверждённый риск потери данных:** `saveQueue()` проглатывает ошибку записи, после чего Telegram offset всё равно сдвигается. При disk full/permission error сообщение потеряется навсегда. Тестов на write failure, auto-drain и понятный статус очереди нет.

### [x] IVA-011 — draft streaming падает на быстром выводе LLM

- **Жалоба:** Telegram нестабильно обрабатывает streaming; при высокой скорости LLM вывод не справляется и падает.
- **Свидетельство:** [обсуждение стриминга, 2026-07-15, msg 7582](https://t.me/aimasters_chat/7582).
- **Ожидаемый результат:** coalescing/дебаунс edits, ограничение частоты, fallback к обычному финальному сообщению.
- **Медиа:** нет.
- **Статус:** закрыт после кросс-валидации.
- **Маршрут:** закрыто; final-only delivery остаётся намеренным KISS-контрактом.
- **Кросс-валидация:** `закрыт намеренным ограничением`. IVA вообще не отправляет draft/edit streaming: Telegram channel обрабатывает только `message.completed`, режет финал на безопасные чанки и имеет HTML → plain fallback.
- **Воспроизведение:** длинный Unicode-текст разбился на 8 Telegram-чанков и собрался обратно без потерь. Это KISS-компромисс: прогрессивного вывода нет, зато заявленная гонка быстрых edits недостижима.

## P2 — производительность и ограничения

### [ ] IVA-012 — высокая idle-нагрузка CPU

- **Жалоба:** на сервере, где остальные процессы занимали 1–3%, IVA поднимала CPU до 80–100% даже без пользовательской нагрузки; после удаления IVA нагрузка исчезла.
- **Свидетельство:** [Freeman, 2026-07-09, msg 7362](https://t.me/aimasters_chat/7362).
- **Медиа:** [скринкаст нагрузки, msg 7362](https://t.me/aimasters_chat/7362) (MP4, 50.9 s).
- **Ожидаемый результат:** профилирование idle poller/workflow, CPU budget и `iva doctor` с причиной активного loop.
- **Статус:** открыт.
- **Маршрут:** research-first; issue создаётся только при воспроизводимой устойчивой idle-нагрузке.
- **Кросс-валидация:** `частично, инцидент не воспроизведён`. Poller использует 30-секундный long poll и 3-секундный backoff; reset умеет остановить сервисы и карантинить workflow state.
- **Наблюдение:** текущие IVA-процессы на VPS были около 0–0.5% CPU. `iva doctor` всё ещё не показывает CPU, restart-rate, размер и активность workflow. Нужен профиль именно во время повторного инцидента.

### [ ] IVA-013 — жёсткие лимиты объёма и harness, рассчитанный на слабые модели

- **Жалоба/архитектурная критика:** пользователь утверждает, что IVA жёстко обрезает объёмы и была рассчитана на модели со слабыми tool-use возможностями.
- **Свидетельство:** [Dzmitry, 2026-07-25, msg 8206](https://t.me/aimasters_chat/8206), детализация [msg 8208](https://t.me/aimasters_chat/8208). Автор не согласился с трактовкой ([msg 8209](https://t.me/aimasters_chat/8209)).
- **Медиа:** нет.
- **Статус:** требует воспроизводимого кейса; не считать подтверждённым багом.
- **Маршрут:** кодовый PR [#59](https://github.com/smixs/iva/issues/59) только для подтверждённого silent truncation в контекстах, которые всегда используют санитайзер; общая критика harness остаётся вне scope.
- **Кросс-валидация:** `частично`. Hard caps реальны: bash 30k, read_file 24k с пагинацией, sanitized inbound context 50k, CORE 1200, persona 800 и grep 1000. Bash/read_file честно сообщают об усечении; 60k queued message, transcript или caption молча превращаются в 50k. Чистый обычный Telegram-текст идёт дальше оригиналом и этим cap не затронут.
- **Что не подтвердилось:** harness берёт context window выбранной модели и включает compaction на 70%; общего session token cap нет. Тезис «рассчитан на слабые модели» кодом не подтверждён. Узкая задача остаётся только для воспроизводимой потери в sanitized context.

## Решение по бэклогу

- **Волна 1, safety prerequisites:** IVA-008 [#51](https://github.com/smixs/iva/issues/51), IVA-001 [#52](https://github.com/smixs/iva/issues/52), IVA-003 [#54](https://github.com/smixs/iva/issues/54). Сначала закрываются потеря данных, неубиваемые процессы и ложный systemd success.

- **Волна 3:** IVA-009 [#53](https://github.com/smixs/iva/issues/53), IVA-005 [#55](https://github.com/smixs/iva/issues/55), IVA-004 [#56](https://github.com/smixs/iva/issues/56). Validator предшествует транзакционному применению config.
- **Волна 4:** IVA-006 [#57](https://github.com/smixs/iva/issues/57), IVA-010 [#58](https://github.com/smixs/iva/issues/58), IVA-013 [#59](https://github.com/smixs/iva/issues/59).
- **Research-first:** IVA-007 и IVA-012. Issue создаётся только после измеримого воспроизведения.
- **Закрыто:** IVA-011 как осознанный final-only Telegram UX.
